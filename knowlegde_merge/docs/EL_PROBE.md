# 实体链接可行性体检（2026-11-21）

> 目的：动手做「实体链接到公开知识库」之前，先量清三件事——**哪些库能用**、**能对上多少**、**对上的对不对**。
> 样本：按度数取高频 100 + 长尾随机 100（度数=2），另外对全部 10,760 个实体复算覆盖率。
> 脚本：`.tmp/el_30_proxy.py` … `.tmp/el_44_safe.py`（编号即执行顺序）。

## 0. 结论先行

| 指标 | 数值 | 口径 |
|---|---|---|
| **Wikidata 候选覆盖率（全量）** | **38.5%**（4,139 / 10,760） | 能检索到至少 1 个候选实体 |
| 高频实体（度数≥50） | **68.0%**（17/25） | 同上 |
| 度数 1 的长尾实体 | 35.6%（2,261/6,344） | 同上 |
| 样本 top100 / random100 | 59% / 45% | 同上 |
| **朴素 top1 精确率** | **75.0%**（48/64，4 个人名无法判定） | 人工逐条判读 68 条命中 |
| **端到端「链接且正确」率** | **24.0%**（48/200） | 正确链接数 ÷ 抽样实体数 |
| 离线词库精确名覆盖率 | 23.7%（2,947/10,760） | zhOnto ∪ Zhishi 词库查名字 |

一句话：**代理通了，Wikidata 能用，覆盖率 38.5%（高频实体 68%）；但如果只是「取搜索第一条」，
十次里有两次半是错的。实体链接的价值全在消歧那一步，不在候选检索。**

## 1. 连通性（代理开启后）

| 目标 | 结果 |
|---|---|
| 本地代理 | **127.0.0.1:7897 可用**（其余 7890/1080/10808 等全部 closed） |
| `wikidata.org/w/api.php` | 200，单请求 **0.8~1.2 秒** |
| `query.wikidata.org/sparql` | 200，批量 50 个名字 **7.3 秒** |
| 并发 | ❌ **5 线程以上大量 ProxyError**，代理会把并发串行化，只能顺序发 |

限流实测：短时间打太多会吃 **429**，要按 `Retry-After` 退避；带 UA 申明用途 + 每批间隔 0.5s 后稳定。

### 批量能力（这是能不能跑全量的关键）

| 方式 | 批量 | 耗时 | 折算 |
|---|---|---|---|
| `wbsearchentities` 单条 | 1 | 1.0s | 10,760 个 ≈ 3 小时 |
| SPARQL + `wikibase:mwapi` 批量搜索 | 25 | 4.1s | 163 ms/实体 |
| 同上 | 50 | 7.3s | **146 ms/实体** |
| 同上 | 100 | 17.4s | 174 ms/实体 |

最终用**每批 50 个、`mwapi:limit 3`**跑完全量，216 批、**26.9 分钟**。

## 3. 精度（人工逐条判读 68 条命中）

判读口径：`correct` = 链接到新闻里指的那个实体（标签不同也算，如 中国→Q148 中华人民共和国）；
`wrong` = 链到同名的别的东西；`unknown` = 人名/代号缺上下文无法判定。

- correct **48**，wrong **16**，unknown 4
- **精确率 75.0%**（48/64，排除 unknown）；unknown 计错则 70.6%
- **端到端正确率 24.0%**（48/200）

16 个判错的，全是同名异义或检索噪声：

## 4. 两个反面实验（重要，别走这两条路）

为了确定「怎么选 top1」，我把两种最直觉的做法都试了，**都失败**：

1. **只按 sitelink 数（Milne-Witten 先验）取最大** → `AI → Q12199 艾滋病`（211 个 sitelink）、
   `北京 → Q578328 美国伊利诺伊州一个小县城`。先验是「同名词条里挑最出名的」，
   一旦候选集里混进了别的词，它只会把错误答案排到第一。
2. **只按标签完全一致过滤，再取先验** → `上海 → Q15036769 1986 年电子游戏`（标签正好是"上海"）、
   `韩国 → Q1574130 战国时期的韩国`、`X光 → Q66124266 1974 年短片`。
   因为 Wikidata 里 `上海市`、`大韩民国` 的标签**不是**你要查的那个字符串，
   严格的字面相等反而把正确答案筛掉了。

结论：候选生成必须**用别名/重定向匹配**（`wbsearchentities` 返回的 `match.type`
能区分 label / alias / description 命中），消歧必须**看上下文**，两条都不能省。

## 6. 建议的落地方式

1. **候选存 3 个，不存 1 个。** 表结构：`entity, qid, label, desc, rank, sitelinks, method, confidence`。
   只写 top1 会把 25% 的错误率固化进图里，而且没法回头修。
2. **宁缺毋滥。** 这批数据 61.5% 的实体在 Wikidata 里没有对应条目（是新产品/事件/机构简称），
   保持 NIL 是正确答案，不是失败。
3. **消歧用上下文，不要只靠先验。** 手里已有现成的上下文——每条三元组都带 `article_id`，
   可以取实体所在文章的标题+摘要做向量，和候选的描述做余弦（BGE-M3 已在环境里）。
   这一步能把「苹果→水果」这类错误摁下去，也是唯一能摁下去的手段。
4. **先做高频。** 度数≥50 的 25 个实体覆盖 68%，改错一个影响面很大；长尾 6,344 个度数 1 的实体
   覆盖率只有 35.6%，收益低，可以最后做。
5. **评测集就用已有的 57 条多源互证三元组**，再抽 100 个人工核对，精度目标定 90% 而不是 100%。
